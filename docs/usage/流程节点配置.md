# 流程节点配置

流程模板存在工作目录 `.kuroe/` 的 `flows.json`，可以手工编辑，也可以 `/flow add <文件>` 导入。文件不存在时用内置「默认」流程。节点分为两层：顶层节点库定义可复用的节点，每条流程用一个根节点把节点装配成图。加载与导入时校验节点库与各条流程，全部非法项一次给出；导入的任一流程不合法就整体不生效。

文件结构：

```json
{
  "Nodes": [
    { "Name": "库节点名", ... }
  ],
  "Flows": [
    {
      "Name": "流程名",
      "Description": "可选说明",
      "Models": [],
      "Nodes": [
        {
          "Name": "根容器名",
          "Nodes": []
        }
      ]
    }
  ]
}
```

## 节点库

顶层 `Nodes` 是节点定义，作为复用单元供流程引用。两种定义：

- **执行节点定义**：声明工具白名单、产出契约与执行方式，不写接线，不声明模型。
- **容器定义**：`Nodes` 子数组组织一组有序成员，`Inputs` 声明传入端口，成员可用 `@端口名` 引用传入内容；`Out` 声明命名输出端口，把内部成员产出透出为容器对外接口。

## 模型选择

`Models` 是按名引用的模型选择。模型选择名只出现在流程装配层：装配层执行节点和引用执行节点用 `Model` 写选择名，引用节点组用 `Models` 把组内模型槽位绑定到选择名。模型选择未写 `Model` 时流程可以加载，但引用它的执行节点无法确定模型，提交任务或启动 run 时报错。

| 字段    | 类型   | 含义                                             |
| ------- | ------ | ------------------------------------------------ |
| `Name`  | string | 模型选择名，流程内唯一且不能为空                 |
| `Model` | string | 使用的模型名，省略时引用它的执行节点无法确定模型 |

## 节点

节点分执行节点与容器两类，写有 `Nodes` 子数组即是容器，否则是执行节点。两类节点共用基础字段：

| 字段      | 类型            | 含义                                                           | 适用 |
| --------- | --------------- | -------------------------------------------------------------- | ---- |
| `Name`    | string          | 节点名，流程/定义内唯一且不能为空                              | 全部 |
| `Gate`    | `Auto`/`Review` | 产出后停在待批准；执行节点产出后、容器成员齐备后               | 全部 |
| `MaxRuns` | int             | 执行次数上限：执行节点为自身配置，容器为组内执行节点的统一默认 | 全部 |

## 引用与装配

流程里的节点可以内联定义，也可以引用节点库定义。引用节点写 `Name`、`Use`，模型由装配层输入：引用执行节点用 `Model` 写模型选择名，引用节点组用 `Models` 绑定组内槽位：

```json
{ "Name": "实施", "Use": "执行", "Model": "执行者" }
```

| 字段      | 含义                                                                   |
| --------- | ---------------------------------------------------------------------- |
| `Use`     | 引用的节点库定义名，引用容器时可用 `In` 与 `Models` 绑定               |
| `Model`   | 引用执行节点时的模型选择名，必须定义在同流程的 `Models` 里             |
| `Models`  | 引用节点组时的模型槽位绑定：槽位名到本流程模型选择名的映射             |
| `In`      | 端口绑定表 | 引用容器：端口名到流程内节点引用的映射，值写 `来源@端口` 或 `@更外层端口`；执行节点不写 `In`，接线一律用 `From` |
| `From`    | 仅引用执行节点时注入接线，指向流程内更早的节点或容器；条目形态见[上游接线](#上游接线) |
| `MaxRuns` | 引用执行节点时覆盖库定义的自身上限，引用容器时覆盖库定义的组内统一上限 |

引用容器时实例名省略则取定义名；引用同一个容器定义多次时必须给不同 `Name`，展开后成员名带 `实例名.` 前缀，实例之间互不冲突。绑定端口必须已由容器定义 `Inputs` 声明。

引用执行节点时 `Model` 必填，模型选择由此从装配层输入；引用节点组时用 `Models` 把组内执行节点的模型槽位绑定为本流程的模型选择名，组内任何槽位未绑定都会在加载时报错。库容器定义内嵌套引用节点组时，`Models` 的绑定值可以是当前节点组可见的槽位名，沿绑定链透传到装配层。

引用节点不带 `Gate`，门控由库定义决定；引用容器不写 `From`。装配层内联容器不声明 `Inputs`，输入端口声明只属于节点库容器定义。

每条流程的 `Nodes` 有且只有一个根节点；根节点通常是承载流程全部内容的容器，可以内联定义，也可以引用库容器定义，还可以是单个执行节点。

容器可声明 `MaxRuns` 作为组内执行节点的统一执行上限：组内执行节点未写自身 `MaxRuns` 时生效，嵌套容器可覆盖外层容器的统一值，执行节点自身配置始终优先。

## 容器

容器定义声明两类端口，构成容器的封装边界：

| 字段      | 类型   | 含义                                                                                       |
| --------- | ------ | ------------------------------------------------------------------------------------------ |
| `Inputs`  | string[] | 传入端口名，成员用 `From: ["@端口名"]` 引用传入内容，引用处用 `In` 绑定来源    |
| `Out`     | object | 命名输出端口表：端口名到内部成员端口的映射，值必须写 `成员@端口` 精确取成员命名段 |

`Inputs` 声明传入端口，取值与绑定见[引用与装配](#引用与装配)：容器定义只声明端口名，引用处用 `In: { "端口名": "来源" }` 绑定当前流程内的实际来源，成员经 `@端口名` 取用。

`Out` 把内部成员产出透出为容器对外接口，可以声明在节点库容器定义与装配层内联容器上，引用节点不可声明。绑定值必须指向容器子树内的执行节点，写 `成员@端口` 取该成员声明的命名端口段或隐式 `ContextOutput`。下游执行节点用 `From: ["容器名@端口"]` 精确消费，编译期解析为对绑定成员执行的依赖。保留名 `Split`、`ContextOutput`、`ContextInput` 不可作输出端口名。

容器是封装边界：装配层及其他容器不能直接引用容器实例内部的成员或成员端口，容器对外只暴露 `Out` 声明的端口。容器没有整份产出，一切对外内容都经声明的命名端口，下游消费必须写 `容器名@端口`。

## 执行节点

执行节点是唯一实际执行的节点，装配层内联定义由以下字段描述。节点库执行定义是复用模板，声明能力字段（工具、契约、模式、分支、拆分），不声明模型与接线；节点库容器定义内的执行成员用 `Model` 写模型槽位名，槽位由引用节点组处的 `Models` 绑定：

| 字段       | 类型                  | 含义                                                                                                                                        |
| ---------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `Model`    | string                | 装配层：引用的模型选择名，必须定义在同流程的 `Models` 里；节点组内：模型槽位名                                                              |
| `Prompt`   | string                | 对执行单元的额外要求，与目标一起构成指令                                                                                                    |
| `Tools`    | string[]              | 能力工具白名单，按工具路径前缀匹配，写上级路径即放行整棵子树；路径按原文大小写敏感比较，非法路径在装配时报错；省略或空时不给出任何能力工具  |
| `Output`   | `Text`/`Plan`/`Input` | 交回什么：普通文本、条目拆分、用户输入，决定收口方式与契约工具                                                                              |
| `Question` | string                | 输入节点的提示文本，等待用户回答时呈现                                                                                                      |
| `Outputs`  | string[]              | 执行节点的命名输出端口表，声明后模型经 `SubmitPortValues` 交回各端口内容，见[输出端口](#输出端口与系统指令) |
| `SystemPrompt` | string[] | 恒定系统指令块，作为系统指令置于请求最前，内容必须恒定以命中服务商前缀缓存，见[输出端口](#输出端口与系统指令) |
| `Mode`     | `Single`/`PerItem`    | 整节点一个 run，还是按拆分条目各启动一个                                                                                                    |
| `Branch`   | string                | 只处理拆分中归属该分支的条目，未写时处理全部条目                                                                                            |
| `From`     | array                 | 上游接线条目：字符串条目必须写 `来源@端口` 或 `@端口`，对象条目带 `Node` 同样必须写来源引用、再加 `Or`、`Signal`、`Context` 键；`Or` 归入可选启动组，`Signal` 只作触发信号不进上下文，`Context` 把产出置于上下文最前，见[上游接线](#上游接线) |
| `Validate` | object                | 输出校验：收口时校验模型产出，不通过则节点阻塞待返工，见[输出校验](#输出校验)                                                               |
| `MaxRuns`  | int                   | 同一执行路径的最高执行次数，达到后不再启动新 run；整节点一条路径，按条目展开时每条目一条路径，未写时继承最近容器的统一配置，最后默认 100    |
| `Split`    | object                | 拆分源的固定配置，只能写在规划执行节点上                                                                                                    |

`Output` 决定收口方式并自动附上契约工具：

- `Text`：模型交回文本产出。
- `Plan`：模型通过 `SubmitPlanItems` 工具交回条目拆分。
- `Input`：不启动 run，输入齐备后停在待用户输入，回答即产出，见[输入节点](#输入节点)。

`Mode: PerItem` 的执行节点按条目展开，条目集来自其引用的规划执行节点，见[依赖与展开](#依赖与展开)。

执行节点库定义不写接线，`From` 由引用处注入；装配层内联执行节点与引用执行节点直接写 `From`。

`From` 条目承载全部上游接线：无标记条目是数据来源，产出进入目标上下文；带 `Signal` 的条目只作触发信号，来源产出不进目标上下文，典型用途是让节点在指定上游跑完后执行、又不想让上游内容暴露给模型；来源再次发布新版本时目标再次启动。带 `Or` 的条目标记可选启动组，组内成员产出一并取用、任一组全齐备即启动。带 `Context` 的条目把来源产出置于目标上下文最前，与系统指令构成稳定前缀。数据与可选组来源全部齐备且任一来源发布未消费的新版本时启动，触发条目只决定启动时机。容器可作来源：容器版本跟随直接成员与子容器的内容版本，任一来源发布新版本且容器重新齐备即触发一次，与执行节点的发布语义一致；成员在执行或停驻时容器暂不齐备，成员恢复放行且来源有已消费过的新版本才再次触发。见[上游接线](#上游接线)。

#### 输入节点

`Output: Input` 的执行节点不启动 run、不需要模型选择：依赖输入齐备后停在「待输入」，用户回答后回答即产出放行下游，下游按依赖边消费。回答经 `Outputs` 声明的端口写入，数据消费须带端口，至多声明一个；未被数据消费可省略声明。`Question` 给提示文本，未写时用通用提示。

输入节点不声明模型与执行配置，`Tools`、`Prompt`、`Mode`、`Branch`、可选启动组、触发信号、上下文输入、`Validate`、`Split` 与 `Gate: Review` 都会被装配校验拒绝；回答见[任务操作](任务操作.md#等待输入)，多个待输入节点时必须指定节点名。

#### 输出端口与系统指令

`Outputs` 给执行节点声明命名输出端口，模型用 `SubmitPortValues` 工具交回「端口名到文本」的 JSON 对象，端口必须与声明一一对应，未交回则节点停在阻塞待返工。文本执行节点、按条目展开的执行节点与输入节点都可声明：PerItem 逐实例交回各自端口值，输入节点至多一个、回答写入该端口。下游用 `From: ["来源@端口"]` 精确消费指定端口。保留名 `Split`、`ContextOutput`、`ContextInput` 不可作命名输出端口。

`SystemPrompt` 声明恒定系统指令块：装配时按序拼接，作为系统指令放在请求最前，与动态内容（对话、上游产出、本轮指令）分离。内容必须恒定，不要拼入任务目标、轮次等动态值；系统指令因此跨轮稳定命中模型服务商的前缀缓存。指令块通常很短，低于服务商的最小缓存粒度时实际不产生命中收益，它的价值是恒定的系统约束；要真正命中缓存，需要把足够长的恒定内容经 `From` 条目的 `Context` 标记接入，见[隐式端口](#隐式端口)。

#### 隐式端口

每个执行节点与容器有保留端口，无需声明、不可写进 `Outputs`：

| 端口 | 方向 | 内容 | 位置 |
| --- | --- | --- | --- |
| `Split` | 输出 | 规划执行节点的拆分支票，专用展开通道，不注入文本 | PerItem 目标 `From: ["规划@拆分"]` 消费，文本背景另写数据边 |
| `ContextOutput` | 输出 | 来源最近成功收口放行 run 的装配上下文：对话、上游产出、条目与指令逐条保留角色与出处，指令单列；上游系统指令只在它自己的请求通道里，不随帧透传 | 下游 `From: ["来源@ContextOutput"]` 消费 |
| `ContextInput` | 输入 | 装配层执行节点用 `From` 条目写 `Context` 标记接入，来源放行产出置于上下文开头，来源须是非输入、非按条目展开的执行节点，内容必须恒定 | 对话之前，与 SystemPrompt 构成稳定前缀段 |

`Split` 与 `ContextOutput` 不需要模型交回，`SubmitPortValues` 不接受它们；输入节点不启动 run，不能作 `ContextOutput` 的来源。`ContextInput` 内容恒定才命中前缀缓存：重复消费相同来源产出时前缀稳定，拼入每轮动态值由使用者自担。

#### 拆分

`Split` 固定规划执行节点的拆分源：

| 字段         | 类型   | 含义                                            |
| ------------ | ------ | ----------------------------------------------- |
| `Items`      | array  | 静态条目清单，1 到 20 条                        |
| `ExtrasMax`  | int    | 模型最多补充的条数，0 到 20，0 或省略表示不补充 |
| `Acceptance` | string | 统一验收文本，覆盖模型补充条目的验收标准        |

静态条目 `Items` 每项：

| 字段          | 类型   | 含义                             |
| ------------- | ------ | -------------------------------- |
| `Title`       | string | 标题，必填                       |
| `Instruction` | string | 要做什么，必填                   |
| `Acceptance`  | string | 该条目的验收标准，省略视为未提供 |
| `Branch`      | string | 归属的分支，省略视为不分流       |

纯静态拆分指定义的 `Items` 非空且 `ExtrasMax` 为 0 或省略，拆分没有模型参与，此时规划执行节点不可声明 `Prompt`、`From` 与 `Gate: Review`。

有分支执行节点从本规划执行节点取拆分时，交回的条目必须写明 `Branch` 且落在已有分支上。

### 容器节点

容器组合执行节点并为子节点限定作用域，自身不执行、不启动 run，成员产出齐备时作汇合点。容器定义额外支持：

| 字段     | 类型     | 含义                                                      |
| -------- | -------- | --------------------------------------------------------- |
| `Nodes`  | array    | 有序子节点，至少一个，整棵子树至少含一个执行节点          |
| `Inputs` | string[] | 输入端口声明，成员可用 `@端口名` 引用，引用处用 `In` 绑定 |

容器不可声明执行配置、`From` 与 `In`。容器可声明 `Gate`，成员齐备后停在待批准。容器门控嵌套时逐层停在待批准：子容器停在待批准时父容器视为未齐备，批准子容器后父容器接续判断；容器成员里的执行节点停在待批准时同样计为成员未放行。

库里容器定义的自包含要求：成员 `From` 只能引用容器定义内部的节点，或 `@` 已声明的输入端口——容器作为整体可被多处引用而不依赖外部名字。

## 依赖与展开

依赖由 `From` 直接表达：引用的执行节点必须先于本节点产出，多个来源的产出一并进入上下文；同一个来源可以派生出多个下游并行推进。边按来源与目标模式在编译期推导消费方式：

| 来源               | 目标      | 消费方式                                            |
| ------------------ | --------- | --------------------------------------------------- |
| 容器               | 任意      | 等整组齐备，按声明的命名端口取值                    |
| 执行节点           | `Single`  | 取来源一整份端口产出                                |
| 执行节点           | `PerItem` | 来源 `PerItem` 时按条目对齐，规划执行节点时按条展开 |
| `PerItem` 执行节点 | `Single`  | 等来源全部条目实例产出齐备                          |

数据来源一律按边上端口取值：执行节点取该端口一份，PerItem 来源按目标模式对齐或拼接全部实例，容器来源取 `Out` 绑定转发。拆分端口 `Split` 只作用于按条目展开的目标，不注入文本内容。

`From: ["来源@ContextOutput"]` 与端口引用同按单份消费：来源最近一次成功放行 run 的整个装配上下文整体注入，逐条保留角色与出处，指令单列，系统指令不随帧透传；PerItem 来源取各实例上下文。`Context` 条目同一来源产出单独置于上下文开头。

按条目展开的执行节点从引用的规划执行节点取条目清单，每条目一个 run。声明 `Branch` 时只处理拆分中归属该分支的条目；分支并行即多个声明不同 `Branch` 的执行节点引用同一个规划执行节点。

### 上游接线

```json
"From": [
  "计划@结论",
  { "Node": "审查@结论", "Or": "修改" },
  { "Node": "通知@结论", "Signal": true },
  { "Node": "背景@结论", "Context": true }
]
```

`From` 是执行节点的唯一接线字段，每条目标记来源引用与消费方式。无标记条目是数据来源，产出进入目标上下文，数据与可选组来源全部齐备且任一来源发布未消费的新版本时启动。带 `Or` 的条目标记可选启动组，组内条目齐备即满足该组，任一组满足即可启动；未声明数据来源时仅需任一组成员齐备。带 `Signal` 的条目不进上下文只作触发信号，有信号条目时由任一信号来源的新版本驱动启动，否则由任一数据或可选组来源的新版本驱动。带 `Context` 的条目把来源产出置于目标上下文最前，与系统指令构成稳定前缀，来源必须是非输入、非按条目展开的执行节点。来源可以是执行节点或容器，信号、可选组与上下文条目按单份消费，数据条目按来源与目标模式推导消费方式。条目引用必须落端口：容器只能写 `容器名@端口`，执行节点写 `来源@端口`，容器成员写 `@端口` 绑定容器传入端口。

`Or` 按组名聚合：同组内条目产出一并取用，同一来源可以跨组重复。条目按 来源与标记 整体判重，完全相同的条目不可重复，带不同标记的同源条目可以并存。声明可选组、信号或上下文的节点必须整节点执行，不与 `PerItem`、纯静态拆分叠用；输入节点不声明可选组、信号与上下文。

库执行定义不写接线，装配层引用处注入的 `From` 就是该实例的全部接线；库容器成员内的执行节点直接写 `From`，引用只落在当前容器作用域内。

执行节点按来源产出版本记账：任一来源重新发布且齐备时重启本节点，启动即登记来源当前版本，同一版本不重复启动。`From` 引用的 PerItem 来源按整份实例一次性消费，实例集重新产出不再次驱动；可选组条目同样按版本记账，任一组发布新版本即驱动该组；信号条目只由信号来源新版本驱动。

### 输出校验

`Validate` 给执行节点一条输出校验规则：run 收口后按声明端口依声明序拼接出的端口文本做判定，未声明端口不能声明 `Validate`。不通过则节点停在阻塞等待返工，产出不发布、不交给下游。校验通过的节点按普通节点推进，同样随来源新版本重启。执行节点引用可以互相指回构成环，环必须有环外来源或环内输入节点才能启动，环内节点随来源新版本互相驱动；校验不通过则停在阻塞，通过则放行，闭环的收敛由输出校验阻塞或 `MaxRuns` 兜底。纯 From 互引做不成环：两个整节点互为前置时谁都不会启动，环内至少一侧必须是可选组或信号提供器节点，重启由它的新版本驱动：

```json
{ "Name": "计划", "Model": "执行者", "Outputs": ["结论"] },
{ "Name": "修订", "Model": "执行者", "Outputs": ["结论"], "From": [{ "Node": "计划@结论", "Or": "初始" }, { "Node": "审查@结论", "Or": "返工" }] },
{ "Name": "审查", "Model": "执行者", "Outputs": ["结论"], "From": ["修订@结论"], "Validate": { "Predicate": "TextContains", "Argument": "通过" } }
```

修订先随「初始」组启动产出初稿；审查对修订产出复核，不通过即停在阻塞；返工重跑审查通过并放行后，「返工」组的新版本再驱动修订重写。审查放行后若不加 `MaxRuns`，修订会被审查新版本继续重写、审查也随之重审，直到任一方到达执行上限，因此这类互驱动环按 `MaxRuns` 封顶收敛。

`Signal` 条目同样构成由来源新版本驱动的迭代环：目标随信号来源发布的新版本重启，环仍需环外来源或环内输入节点才能启动，收敛由输出校验或 `MaxRuns` 兜底，见[上游接线](#上游接线)。

| 字段        | 类型   | 含义                                                           |
| ----------- | ------ | -------------------------------------------------------------- |
| `Predicate` | enum   | `NonEmpty`、`TextContains`、`TextNot`、`TextEquals`、`Pattern` |
| `Argument`  | string | 谓词参数：指定文本或正则，`NonEmpty` 不需要                    |

声明 `Validate` 的节点必须整节点执行，不与 `PerItem` 或纯静态拆分叠用。校验失败后节点停在阻塞，返工目标即节点自身，重跑后再校验。环由引用自然产生；同一条执行路径的执行次数达到 `MaxRuns` 上限后不再重启。

### 对话环

含输入节点的环把输入节点当挂点：输入节点任务启动即停驻等待回答，每轮回答发布后沿环推进，回到输入节点时产出被消费并复位，重新挂着等下一轮，对话由此一轮接一轮。输入节点是周期外源，不依赖环形态即作为每轮起点，见[依赖与展开](#依赖与展开)。

```json
{ "Name": "收话", "Output": "Input", "Outputs": ["回答"], "From": ["回话@回复"] },
{ "Name": "回话", "Model": "执行者", "Outputs": ["回复"], "From": ["收话@回答"] }
```

## 校验规则

启动时逐条校验，全部非法项一次给出。规则即任务推进依赖的不变量：

- 每条流程有且只有一个根节点。
- 节点库名非空且库内唯一，节点库定义不能是引用自身。
- 节点名不能为空且流程内唯一，模型选择名不能为空且流程内唯一。
- 节点引用的模型选择必须存在，引用的节点库定义必须存在。
- 节点库执行定义与容器定义不声明模型，节点组内执行成员必须写模型槽位名。
- 装配层执行节点与引用执行节点必须写模型选择名，且必须存在于同流程的 `Models`，未写或不存在报错。
- 引用节点组的 `Models` 绑定覆盖组内全部模型槽位，未绑定的槽位在加载时报错；引用执行节点不写 `Models`，引用节点组不写 `Model`。
- 执行节点库定义不写 `Inputs`、`From` 与 `In`；容器定义不写执行配置、`From` 与 `In`；引用节点不写执行配置、子节点、`Inputs` 与 `Gate`，引用容器不写 `From`。
- 引用节点不能同时声明执行配置或子节点，绑定端口必须已由容器定义声明。
- 容器定义自包含：成员 `From` 只指向定义内部节点或已声明端口，至少要包含一个执行节点。
- 容器输出端口：可声明在节点库容器定义与装配层内联容器上，引用节点不可声明；绑定值必须指向容器子树内的执行节点，写 `成员@端口`，该端口必须是目标成员声明的命名输出端口或隐式 `ContextOutput`；输入节点与子容器不可作绑定目标；端口名不与保留名 `Split`、`ContextOutput`、`ContextInput` 冲突。
- 容器外不能直接引用容器实例内部的成员或成员端口，`From` 条目必须落在引用节点的容器作用域内，或经容器 `Out` 端口消费。
- `From` 引用必须存在；容器不可被引用为容器的输入，但可作为执行节点的来源。
- 引用关系按容器成员展开后，环必须有环外来源或环内输入节点才能启动；成员只从自身所在容器取输入视为无法启动。
- `From` 条目引用的来源必须存在；条目按 来源与标记 整体判重，完全相同的条目不可重复，带不同标记的同源条目可以并存，同一来源可跨可选组重复；容器不可被引用为容器的输入，但可作为执行节点的来源。
- 引用节点组不声明 `From` 与 `Validate`，两者只属于执行节点；引用容器可声明 `MaxRuns` 覆盖库定义的组内统一上限。
- `MaxRuns` 必须是正整数：执行节点为自身上限，容器为组内执行节点的统一默认，未写时继承最近容器的统一配置，最后默认 100；同一执行路径达到上限后不再启动新 run。
- 声明 `Validate` 的节点必须整节点执行，不支持纯静态拆分，且必须声明至少一个输出端口供校验取文本；`Predicate` 必须是白名单内的名字，需要参数的谓词必须给参数，`Pattern` 的正则必须合法。
- 按条目展开的执行节点必须从规划执行节点取拆分，或从其它展开执行节点对齐输入。
- 声明 `Branch` 的执行节点必须按条目展开并从规划执行节点取拆分；逐条对齐的两端必须来自同一个拆分。
- `Split` 只写在规划执行节点上。
- 输入节点不启动 run，不需要模型选择，也不接受 `Tools`、`Prompt`、`Mode`、`Branch`、可选启动组、触发信号、上下文输入、`Validate`、`Split` 与 `Review` 门控。
- 输出端口可声明在文本执行节点、按条目展开的执行节点与输入节点上，输入节点至多一个、回答写入该端口；声明后必须经 `SubmitPortValues` 交回全部端口内容，下游 `From` 引用的端口必须存在，引用一律写 `来源@端口`；保留名 `Split`、`ContextOutput`、`ContextInput` 不可写进 `Outputs`。
- `From: ["来源@ContextOutput"]` 消费来源最近成功放行 run 的装配上下文，不含来源的系统指令，来源必须是执行节点，输入节点不落 run 不可作来源。
- 装配层执行节点用 `From` 条目的 `Context` 标记接入隐式上下文输入端口，来源必须是流程里的非输入、非按条目展开的执行节点，只能写节点名或 `来源@端口`，不能引容器或绑定端口。
- `SystemPrompt` 只能声明在非输入执行节点上，内容必须恒定，不能拼入任务动态值；`Context` 条目的来源产出同样必须恒定以命中前缀缓存。

## 内置流程

`flows.json` 不存在或 `DefaultFlow` 未写入用户层时，用内置「默认」流程：制定计划 → 分配执行。内置内容本身就是节点库加装配：库定义规划、执行两个执行节点与「交付」容器，流程用根容器包住「制定计划」与「交付」两个引用；装配层从外部输入模型，「制定计划」写规划者配置，「交付」把执行者配置绑定给组内实施节点。两个模型选择都不写 `Model`，流程可加载但执行时无法确定模型。
