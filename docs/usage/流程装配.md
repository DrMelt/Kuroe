# 流程装配

流程里的节点可以内联定义，也可以引用节点库定义；引用节点写 `Name`、`Use`，模型由装配层输入。每条流程的 `Nodes` 有且只有一个根节点，根节点通常是承载流程全部内容的容器，可以内联定义，也可以引用库容器定义，还可以是单个执行节点。流程的起点是 `Start` 声明的来源节点，节点名即保留名 `Start`，它是唯一的来源，一切节点经 `From` 引用它取用初始输入；节点字段见[节点定义](节点定义.md)，节点库与文件装载见[流程文件与节点库](流程文件与节点库.md)。

## 模型选择

`Models` 在流程层是按名引用的模型选择。模型选择名只出现在流程装配层：装配层执行节点和引用执行节点用 `Model` 写选择名，引用节点组用 `Models` 把组内模型槽位绑定到选择名。模型选择未写 `Model` 时流程可以加载，但引用它的执行节点无法确定模型，提交任务或启动 run 时报错。节点库容器定义用 `Models` 声明槽位，见[容器定义](节点定义.md#容器定义)。

| 字段    | 类型   | 含义                                             |
| ------- | ------ | ------------------------------------------------ |
| `Name`  | string | 模型选择名，流程内唯一且不能为空                 |
| `Model` | string | 使用的模型名，省略时引用它的执行节点无法确定模型 |

## 引用与装配

引用节点写 `Name`、`Use`，模型由装配层输入：引用执行节点用 `Model` 写模型选择名，引用节点组用 `Models` 绑定组内槽位：

```json
{ "Name": "实施", "Use": "执行", "Model": "执行者" }
```

| 字段      | 含义                                                                   |
| --------- | ---------------------------------------------------------------------- |
| `Use`     | 引用的节点库定义名，引用容器时可用 `In` 与 `Models` 绑定               |
| `Model`   | 引用执行节点时的模型选择名，必须定义在同流程的 `Models` 里             |
| `Models`  | 引用节点组时的模型槽位绑定：槽位名到本流程模型选择名的映射             |
| `In`      | 端口绑定表：引用容器时端口名到流程内节点引用的映射，值写 `来源@端口` 或 `@更外层端口`；执行节点不写 `In`，接线一律用 `From` |
| `From`    | 仅引用执行节点时注入接线，指向流程内更早的节点或容器；组的形态见[上游接线](#上游接线) |
| `MaxRuns` | 引用执行节点时覆盖库定义的自身上限，引用容器时覆盖库定义的组内统一上限 |

引用容器时实例名省略则取定义名；引用同一个容器定义多次时必须给不同 `Name`。展开后成员沿用定义里写下的名字，层级由树位置给出，实例之间以路径区分，同一成员名可以出现在多个实例里。绑定端口必须已由容器定义 `Inputs` 声明。

引用执行节点时 `Model` 必填，模型选择由此从装配层输入；引用节点组时用 `Models` 把组内执行节点的模型槽位绑定为本流程的模型选择名，绑定键必须与容器定义的槽位声明一一对应，未绑定或绑定声明以外的槽位都在加载时报错。库容器定义内嵌套引用节点组时，`Models` 的绑定值可以是当前容器声明的槽位名，沿绑定链透传到装配层。

引用容器不写 `From`。装配层内联容器不声明 `Inputs`，输入端口声明只属于节点库容器定义。

装配层及其他容器不能直接引用容器实例内部的成员或成员端口，下游消费必须写 `容器名@端口`，容器对外只暴露 `Outputs` 声明的端口。

## 依赖与展开

依赖由 `From` 直接表达：引用的执行节点必须先于本节点产出，多个来源的产出一并进入上下文；同一个来源可以派生出多个下游并行推进。边按来源与目标模式在编译期推导角色与消费方式，边只有两种角色：取值，或为按条目目标提供实例空间：

| 来源               | 目标      | 边的角色与消费方式                                            |
| ------------------ | --------- | ------------------------------------------------------------- |
| Start              | 任意      | 取值，取端口一份；带 `Value` 的端口给固定值，其余端口给提交任务的初始输入 |
| 容器               | 任意      | 取值，来源齐备后按声明的命名端口取一份                        |
| 执行节点           | `Single`  | 取值，取来源一整份端口产出                                    |
| 执行节点           | `PerItem` | 来源 `PerItem` 时取值并按条目对齐，声明 `WorkItems` 端口的执行节点时提供实例空间 |
| `PerItem` 执行节点 | `Single`  | 取值，等来源全部条目实例产出齐备，整套只消费一次              |

取值边另有取值域与消费次数两项：取值域为整份产出、来源全部实例的产出、或与目标同序号的实例产出；消费次数为每次新版本都消费，或整套只消费一次。来源是 `PerItem` 且目标是 `Single` 时按后者消费，其余按版本消费。

数据来源一律按边上端口取值：执行节点取该端口一份，PerItem 来源按目标模式对齐或拼接全部实例，容器来源取 `Outputs` 绑定转发。声明 `WorkItems` 类型端口的来源在按条目目标上提供实例空间，不注入文本内容。开始可声明多个 `Text` 端口，带 `Value` 的端口固定输出该值，不带 `Value` 的端口输出提交任务的初始输入，下游按端口精确消费。

`From: [{ "上下文": "来源@上下文" }]` 按单份消费：来源最近一次成功放行 run 的整个装配上下文整体注入，逐条保留角色与出处，指令单列，系统指令不随帧透传；PerItem 来源取各实例上下文。`Type: Context` 的输入端口把来源产出单独置于上下文开头。

按条目展开的执行节点从引用的拆分源取条目清单，每条目一个 run。声明 `Branch` 时只处理拆分中归属该分支的条目；分支并行即多个声明不同 `Branch` 的执行节点引用同一个拆分源。

### 上游接线

```json
"From": [
  { "计划": "计划@结论" },
  { "计划": "评审@结论" }
]
```

`From` 是执行节点的唯一接线字段，数组元素是一个启动组，组内是目标输入端口名到来源端口引用的映射。组间任一齐备即启动，组内全部齐备。

输入端口的类型决定来源产出如何接进目标：`Text` 按序注入上下文并参与齐备判定；`Context` 置于上下文最前，与系统指令构成稳定前缀，来源必须是非输入、非按条目展开的执行节点；`Signal` 不消费内容，只在组内以来源的新版本驱动启动，输入节点声明 `Signal` 输入端口表示该连接只作环的回边驱动。类型写在目标节点的 `Inputs` 声明上，见[输入端口](节点定义.md#输入端口)。未声明 `Inputs` 时连接键按 `Text` 类型处理。

来源可以是执行节点或容器，连接必须落端口：容器只能写 `容器名@端口`，执行节点写 `来源@端口`，容器成员写 `@端口` 绑定容器传入端口。每个组必须覆盖节点声明的全部输入端口，组内输入名唯一，组间来源端口不重复，为按条目目标提供实例空间的连接除外。

库执行定义不写接线，装配层引用处注入的 `From` 就是该实例的全部接线；库容器成员内的执行节点直接写 `From`，引用只落在当前容器作用域内。

整节点执行节点按来源产出版本记账：任一组内的来源重新发布且该组齐备时重启本节点，启动即登记来源当前版本，同一版本不重复启动。`From` 引用的 PerItem 来源按整份实例一次性消费，实例集重新产出不再次驱动；组内有信号输入时只由该组信号来源的新版本驱动，否则由组内任一来源的新版本驱动。

按条目展开的执行节点逐实例启动：条目取自实例空间，某条目没有产出且任一组齐备即启动该条目，一条目只跑一次；返工作废后条目回到未产出，随下一次齐备重启。实例空间在首次确定后固定，拆分来源重新交回不追加条目。

容器与执行节点共用同一套输入侧判定与同一份消费账：容器版本跟随直接成员与子容器的内容版本，任一来源发布新版本且成员与子容器全部放行即触发一次，与执行节点的发布语义一致；成员在执行或停驻时容器暂不齐备，成员恢复放行且来源有已消费过的新版本才再次触发。

### 输出校验

`Validate` 给执行节点一条输出校验规则：run 收口后按声明端口依声明序拼接出的端口文本做判定，未声明端口不能声明 `Validate`。不通过则节点停在阻塞等待返工，产出不发布、不交给下游。校验通过的节点按普通节点推进，同样随来源新版本重启。执行节点引用可以互相指回构成环，环必须有环外来源或环内输入节点才能启动，环内节点随来源新版本互相驱动；校验不通过则停在阻塞，通过则放行，闭环的收敛由输出校验阻塞或 `MaxRuns` 兜底。纯单组 `From` 互引做不成环：两个整节点互为前置时谁都不会启动，环内至少一侧必须给出多个启动组或有信号输入来提供新版本驱动：

```json
{ "Name": "计划", "Kind": "Llm", "Model": "执行者", "Outputs": [{ "Name": "结论", "Type": "Text" }] },
{ "Name": "修订", "Kind": "Llm", "Model": "执行者", "Outputs": [{ "Name": "结论", "Type": "Text" }], "From": [{ "计划": "计划@结论" }, { "审查": "审查@结论" }] },
{ "Name": "审查", "Kind": "Llm", "Model": "执行者", "Outputs": [{ "Name": "结论", "Type": "Text" }], "From": [{ "修订": "修订@结论" }], "Validate": { "Predicate": "TextContains", "Argument": "通过" } }
```

修订先随「计划」组启动产出初稿；审查对修订产出复核，不通过即停在阻塞；返工重跑审查通过并放行后，「审查」组的新版本再驱动修订重写。审查放行后若不加 `MaxRuns`，修订会被审查新版本继续重写、审查也随之重审，直到任一方到达执行上限，因此这类互驱动环按 `MaxRuns` 封顶收敛。

`Type: Signal` 的输入端口同样构成由来源新版本驱动的迭代环：目标随信号来源发布的新版本重启，环仍需环外来源或环内输入节点才能启动，收敛由输出校验或 `MaxRuns` 兜底，见[上游接线](#上游接线)。

| 字段        | 类型   | 含义                                                           |
| ----------- | ------ | -------------------------------------------------------------- |
| `Predicate` | enum   | `NonEmpty`、`TextContains`、`TextNot`、`TextEquals`、`Pattern` |
| `Argument`  | string | 谓词参数：指定文本或正则，`NonEmpty` 不需要                    |

声明 `Validate` 的节点必须整节点执行，必须声明至少一个 `Text` 输出端口供校验取文本，不与 `PerItem` 叠用；`Predicate` 必须是白名单内的名字，需要参数的谓词必须给参数，`Pattern` 的正则必须合法。校验失败后节点停在阻塞，返工目标即节点自身，重跑后再校验。环由引用自然产生；同一条执行路径的执行次数达到 `MaxRuns` 上限后不再重启。

### 对话环

含输入节点的环把输入节点当挂点：输入节点由 `From` 里的 `Start@端口` 触发，进入等待回答，每轮回答发布后沿环推进，回到输入节点时产出被消费并复位，重新挂着等下一轮，对话由此一轮接一轮。输入节点每轮从外部接收回答，是周期外源，但仍要由开始入口触发第一次挂起，见[依赖与展开](#依赖与展开)。回复内容由回话的 run 结果交给调用方，环的回边只作驱动，收话消费回复的输入端口因此声明为 `Signal`。

```json
{ "Name": "收话", "Kind": "Input", "Inputs": [{ "Name": "目标" }, { "Name": "回复", "Type": "Signal" }], "Outputs": [{ "Name": "回答", "Type": "Text" }], "From": [{ "目标": "Start@目标", "回复": "回话@回复" }] },
{ "Name": "回话", "Kind": "Llm", "Model": "执行者", "Outputs": [{ "Name": "回复", "Type": "Text" }], "From": [{ "回答": "收话@回答" }] }
```

## 校验规则

启动时逐条校验，全部非法项一次给出。库定义与装载规则见[流程文件与节点库](流程文件与节点库.md#校验规则)，节点形状规则见[节点定义](节点定义.md#校验规则)：

- 每条流程有且只有一个根节点。
- 流程必须声明 `Start`，恰好一个不带 `Value` 的 `Text` 端口承接提交任务的初始输入，其余端口必须带 `Value`；节点名 `Start` 是保留名。
- 每个执行节点、输入节点与审批节点都必须能从开始经 `From` 引用边到达，否则不会被触发。
- 模型选择名不能为空且流程内唯一；节点引用的模型选择必须存在，引用的节点库定义必须存在。
- 装配层执行节点与引用执行节点必须写模型选择名，且必须存在于同流程的 `Models`，未写或不存在报错。
- 引用节点组的 `Models` 绑定与容器定义的槽位声明一一对应：未绑定或绑定声明以外的槽位在加载时报错；引用执行节点不写 `Models`，引用节点组不写 `Model`。
- 引用节点不写执行配置、子节点与 `Inputs`，引用容器不写 `From`；引用节点组不声明 `From` 与 `Validate`，两者只属于执行节点。
- 引用节点不能同时声明执行配置、`Question` 或子节点，绑定端口必须已由容器定义声明。
- 容器外不能直接引用容器实例内部的成员或成员端口，`From` 连接必须落在引用节点的容器作用域内，或经容器 `Outputs` 端口消费。
- `From` 连接引用的来源必须存在；来源名按作用域链解析：从引用处所在容器逐层向外，每层先看直接子节点再看子树，`Start` 是流程级来源，任何作用域都能引用。每个组覆盖节点声明的全部输入端口，组内输入名唯一，组间来源端口不重复，为按条目目标提供实例空间的连接除外，连接键必须落在声明内。
- 容器不可被引用为容器的输入，但可作为执行节点的来源。
- 引用关系按容器成员展开后，环必须有环外来源或环内输入节点才能启动；成员只从自身所在容器取输入视为无法启动。
- 按条目展开的执行节点必须能确定实例空间：从声明 `WorkItems` 端口的执行节点取拆分，或从其它展开执行节点对齐取实例集；拆分来源只能有一个，多个来源的条目无法归属同一个实例空间。
- 声明 `Branch` 的执行节点必须按条目展开并从声明 `WorkItems` 端口的执行节点取拆分；逐条对齐的两端必须来自同一个拆分。
- 节点声明的输入端口名与输出端口名各自在同一节点内唯一，输入端口类型只能是 `Text`、`Context` 或 `Signal`，输出端口类型只能是 `Text`、`WorkItems` 或 `Context`，审批节点由输入端口派生的输出端口还可为 `Signal`。
- `WorkItems` 输出端口只能被按条目展开的执行节点消费，或作 `Signal` 驱动；声明 `Context` 输入端口的执行节点不能按条目展开。
- `From: [{ "输入名": "来源@上下文" }]` 消费来源声明的 `Context` 输出端口，注入来源最近成功放行 run 的装配上下文，不含来源的系统指令，来源必须是执行节点，输入节点不落 run 不可作来源。
- 声明 `Type: Context` 输入端口的节点把来源产出接入上下文前缀段，来源必须是流程里的非输入、非按条目展开的执行节点，只能写节点名或 `来源@端口`，不能引容器或绑定端口；来源产出必须恒定以命中前缀缓存。
- 同一执行路径的执行次数达到 `MaxRuns` 上限后不再启动新 run。

## 示例

下面是一份完整的流程文件，场景是按大纲撰写文档：节点库把按条撰写与合成全文两个执行能力定义成可复用节点，再用容器「成稿」把它们组装成先逐章撰写、再合成全文的交付单元；两条流程都引用「成稿」，模型由各自装配层从外部输入。节点库不写模型，「成稿」用 `Models` 声明组内成员需要的模型槽位，成员用 `Model` 写槽位名，流程引用容器时用 `Models` 把槽位绑定到本流程的模型选择：

```json
{
  "Nodes": [
    {
      "Name": "撰写章节",
      "Kind": "Llm",
      "Prompt": "按大纲条目逐节撰写正文。",
      "Tools": ["files"],
      "Mode": "PerItem",
      "Inputs": [{ "Name": "条目", "Description": "待撰写的章节条目。" }],
      "Outputs": [{ "Name": "正文", "Type": "Text" }]
    },
    {
      "Name": "合成全文",
      "Kind": "Llm",
      "Prompt": "把各章节正文合成一篇完整文档。",
      "Inputs": [{ "Name": "正文", "Description": "各章节正文。" }],
      "Outputs": [{ "Name": "全文", "Type": "Text" }]
    },
    {
      "Name": "成稿",
      "Kind": "Container",
      "Models": ["章节作者", "统稿者"],
      "Inputs": [{ "Name": "大纲", "Description": "待撰写的章节条目，来自规划节点。" }],
      "Outputs": [{ "Name": "全文", "Ref": "合成@全文" }],
      "Nodes": [
        { "Name": "撰写", "Use": "撰写章节", "Model": "章节作者", "From": [{ "条目": "@大纲" }] },
        { "Name": "合成", "Use": "合成全文", "Model": "统稿者", "From": [{ "正文": "撰写@正文" }] }
      ]
    }
  ],
  "Flows": [
    {
      "Name": "单线撰写",
      "Description": "制定大纲后逐章撰写并合成，按容器输出端口校对",
      "Models": [
        { "Name": "规划者", "Model": "<模型>" },
        { "Name": "章节作者", "Model": "<模型>" },
        { "Name": "统稿者", "Model": "<模型>" },
        { "Name": "校对者", "Model": "<模型>" }
      ],
      "Start": { "Outputs": [{ "Name": "目标", "Type": "Text" }] },
      "Nodes": [
        {
          "Name": "整体",
```
