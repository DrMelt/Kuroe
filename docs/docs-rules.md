# 文档分层与维护规则

同一事实只允许有一处，别处写路径指向它；读代码五分钟就能得到的东西不进任何一层：字段清单、方法签名、目录列表。

统一用词：代码级调用口写接口，数据格式与容器写格式定义，跨模块行为与数据语义写约定。代码中已用 Contract 命名的类型按原名引用。

文档以技术文档风格编写，直白且准确，不用括号，不用装饰性语言。

依赖事实以工程文件的项目引用为准，依赖图是它的呈现，各文档的依赖段与两者保持一致。

## architecture

`dev/architecture/architecture.md` 给出项目划分、依赖图与索引。

- 只写全景：项目定位、依赖图、索引表。
- 依赖图与项目引用一一对应，节点只带最短定位。
- 索引表按域分组，给出模块与边界文档链接，不重复模块职责。

## functional_boundary

`dev/architecture/functional_boundary/` 按域分子目录，一模块一篇。

- 目录名与索引表的域一致，模块文档放在所属域目录下。
- 结构固定为简介、职责、边界外、依赖四段。
- 简介一句话定性，必要时点出与其他模块的分工。
- 职责由行为承诺组成：应能描述模块负责什么，说不出它内部怎么实现。
- 跨模块约束可以写：义务归属、传递可见性与门控条件；不写流程步骤。
- 不写具体类型名、成员名与常量名，也不写外部库与框架名。
- 文件名 slug 由项目名点号改连字符、全小写得到，例如 `kernel/kuroe-execution-shared.md`。
- 跨文档引用写相对链接，路径以引用方所在目录为基准；只声明归属时写项目名。

## mechanism

`dev/architecture/mechanism/` 记录跨模块协作机制，一主题一篇。

- 写时序、类型名、方法名与扩展点，这是本层的价值所在。
- 不写模块内部实现，不重复边界文档的职责描述。
- 只写跨模块的部分，单个模块内的推进归该模块边界文档。

## libraries

`dev/libraries/` 记录第三方库中读代码难以掌握的机制，一主题一篇。

- 写类型名、方法名、时序与扩展点。
- 不写本项目模块的边界与职责。
- 文件名用主题名，不带项目名。
